Building Production LLM Pipelines: Lessons from the Trenches

May 2025 8 min read
LLM Engineering FastAPI Production

There's a significant gap between "running an LLM in a notebook" and "running an LLM reliably in production for thousands of users." Having spent the last few years building and operating LLM systems at scale, I want to share the patterns that have worked and the mistakes I've made along the way.

The Async Architecture Decision Is Make-or-Break

The most consequential early decision in any LLM pipeline is whether to run synchronously or asynchronously. For anything beyond a simple chatbot, the answer is almost always async — but the reasoning matters.

LLM inference is slow. A complex chain with multiple model calls, retrieval, and tool use can easily take 30–120 seconds. If you expose that as a synchronous HTTP endpoint, you're going to hit connection timeouts, your users will stare at loading spinners, and your servers will be pinned waiting for model responses.

The pattern I've landed on is a FastAPI + Celery + RabbitMQ stack:

  • FastAPI accepts the request, validates input, and immediately returns a task ID
  • Celery workers consume from the queue and handle the actual LLM work
  • Clients poll for status or receive a webhook callback when done

This decouples request acceptance from processing, lets you scale workers independently, and gives you natural retry semantics for failures. 

# Simplified task submission pattern
@app.post("/tasks/translate")
async def submit_translation(request: TranslationRequest) -> TaskResponse:
    task_id = str(uuid4())
    task = run_translation.delay(
        task_id=task_id,
        content=request.content,
        target_language=request.language,
    )
    return TaskResponse(task_id=task_id, status="queued")

@app.get("/tasks/{task_id}")
async def get_task_status(task_id: str) -> TaskStatusResponse:
    result = AsyncResult(task_id)
    return TaskStatusResponse(
        task_id=task_id,
        status=result.status,
        result=result.result if result.ready() else None,
    )

Evaluation Infrastructure Is Not Optional

One of the biggest mistakes I made early was treating LLM evaluation as something to "do later." The problem with LLMs is that they degrade silently. A model provider updates their API, your prompt templates shift slightly, and suddenly your outputs are worse — but you have no automated signal telling you that.

The minimum viable evaluation stack I now set up from the start:

  • A golden dataset — 50–200 hand-curated input/output pairs covering your core use cases and edge cases
  • Automated scoring — LLM-as-a-judge for semantic quality, plus deterministic checks for format and constraints
  • Regression gates — CI/CD step that blocks deploys if eval scores drop more than X% versus baseline
  • Tracing — LangFuse or similar to log every prompt/completion pair in production

The combination of a golden dataset and tracing lets you do something powerful: when you see a production failure, you can add that case to your golden set, reproduce it locally, and verify your fix before deploying.

Prompt Engineering at Scale

Prompt engineering stops being about clever phrasing once you're at scale. The challenges become:

  • Version control — prompts need to be versioned like code, with a clear process for testing changes
  • Parameterization — large portions of your prompt are dynamic; keeping templates readable matters
  • Context window management — you will hit limits; you need explicit strategies for what to truncate and how
  • Model-specific tuning — the same prompt behaves differently across GPT-4, Claude, and Llama; abstract this cleanly

I treat prompts as first-class artifacts with their own test coverage. A prompt change goes through the same review process as a code change — because functionally, it is one.

Failure Modes to Anticipate

Here are the failure modes that have surprised me most in production, roughly in order of how often I've encountered them:

  1. Model API rate limiting — implement exponential backoff from day one, not as an afterthought
  2. Non-deterministic outputs breaking downstream parsing — always validate structured output schemas; never trust that the model will return valid JSON
  3. Context drift in long chains — earlier parts of a long pipeline influencing later steps in unexpected ways; add explicit context resets
  4. Cost explosions from runaway retries — set hard budget limits per task; a retry loop hitting a confused model can burn significant spend
  5. Silent quality degradation — addressed by evaluation infrastructure above, but it's common enough to call out twice

Observability Is Leverage

Every hour I've invested in observability has paid back many times over. At minimum, log:

  • Task ID, model used, prompt version, and output for every LLM call
  • Latency at each stage of your pipeline (not just end-to-end)
  • Token counts (input and output) for cost tracking
  • Any validation failures or retry events

When you're debugging a production issue at 2am, rich traces are the difference between a 10-minute fix and a 3-hour investigation.

Closing Thoughts

The core insight from years of this work: LLM engineering is less about the models and more about the infrastructure around them. The model is just a function call. The hard problems are reliability, observability, evaluation, and cost management — the same problems you'd face with any unreliable external dependency, just with a unique failure mode taxonomy.

Build the boring infrastructure first. The creative prompt work is more fun, but it's the scaffolding that determines whether your system survives contact with production.
